# Research note

When it comes to agentic coding, a lot of people still spend time checking the agent's work. Some old-school elite engineers still read every line of AI-generated code. Simon Willison (2025), one of the creators of Django, won't commit code "if I couldn't explain exactly what it does to somebody else." People who can't fully understand the code, like most students in this course, work differently. They describe their feature to the agent in a sentence or two, the agent finishes it, they click around by hand, find a few bugs, send them back, and go round and round.
 
Either way, the human is still the one doing the checking, by reading the code or by poking at the app. In my opinion, a good agent developer should work more like the lead of a cross-functional team, and put their attention on the product and the team. They should design a workflow where one agent's work gets checked by another agent, so they can spend more time thinking about what to build and what counts as good.
 
Leads at tech companies already work like this. At my last job at a large tech company, the leads I worked with almost never read our code or tested the product themselves. Instead they relied on a whole system to keep the quality up, like the number of bugs QA found before a release, the incidents and crash rates after it, and feedback from senior engineers. That left their time free for priorities and trade-offs. Now agents are pushing every developer into that job. Andrew Ng (2025) argues that once agents write the code, "deciding what to build is the new bottleneck".
 
But there is one big difference. In a human team, the person checking the code is not the person who wrote it. In an agent team they can be the same agent, and that agent will bend any check it can reach. Anthropic (2025, p. 22) admits that Claude 3.7 Sonnet sometimes passed tests by "directly returning expected test values", and METR says this is "a general phenomenon, not isolated to any one model or developer" (Von Arx et al., 2025). The same report explains how it was caught. "User testing did not identify this behavior", but automated classifiers running separately from the model did. The agent understands the task fine, it just chases the score, so I don't think better prompts will fix this. What works is a check the agent can't reach, and building that independence is the agent developer's job. They have to decide what counts as done, who checks it, and what the coding agent is not allowed to touch.
 
Anthropic and OpenAI both build their own workflows around this. Anthropic tells developers to "Have one Claude write code; use another Claude to verify", and to tell the coder "not to modify the tests" (Cherny, 2025). I find the second part interesting, because Anthropic wouldn't need to write that warning if Claude didn't keep doing it. So even the company that makes the model doesn't trust it to grade its own work. OpenAI's Codex team goes even further. Humans there "may review pull requests, but aren't required to", and when the agent ignores a written rule, they "promote the rule into code" (Lopopolo, 2026). In other words, they turn the rule into a check that fails whenever it is broken. Of course, both companies sell agents, so they want you to use more of them. Still, two competitors ended up with the same setup on their own, and so did I. In my project a pm agent writes acceptance criteria that I settle, and a qa agent writes tests from them without reading the code. My design rule also started as a line in CLAUDE.md and ended up as a hook (see PROCESS.md).
 
The biggest objection comes from Dijkstra (1972), who said testing "can be a very effective way to show the presence of bugs, but is hopelessly inadequate for showing their absence." Tests only cover the cases someone thought of, so if no human reads the code, bugs in every other case get shipped. I agree with Dijkstra about tests, but I don't think reading code is the answer. When a reviewer catches a bug, it is usually because they thought of a case the author missed, like an empty input or two users acting at once. If that case gets written into the acceptance criteria, a test checks it on every future change. If it stays in the reviewer's head, it gets checked once. What tests really can't catch is a wrong requirement, because then the code passes every check and is still wrong. Carlini (2026), who built a C compiler with a team of Claude agents and spent most of his effort on their tests, still calls deploying software nobody has personally verified "a real concern". He is right to worry, but to me that means spending more time on what the checks cover, not going back to reading every line.
 
So I think the field should train developers differently, not to read every line, but to decide what is worth building, to write down what good means clearly enough for a machine to check, and to design who checks whom. This still needs engineering knowledge, because you can only decide what to check if you know where code usually breaks.
